# DanceForm backend pilot

Hosted target design and local pilot status · 23 November 2026.

The runnable local pilot now uses Node 24.12 built-in HTTP/SQLite with no server runtime dependencies: [entry point](../apps/server/index.mjs), [API](../apps/server/server.mjs), [durable store](../apps/server/storage.mjs), and [integration tests](../tests/server.test.mjs). Drafts, immutable published revisions, audio files, scoped revocable reader links, notes, and explicit acknowledgments persist under `DATA_DIR` (default `.data`). Autosave uses expected-version conflict checks. Published reads and mutations require the appropriate editor/reader capability. This implementation intentionally differs from the managed hosted target below; Supabase, a distributed worker queue, and hosted accounts have not been provisioned.

Current verification: 11 server integration tests pass locally, covering durable restart, optimistic conflicts, publication review/blocking, reader isolation/revocation, notes/acknowledgments, real-byte audio persistence/range responses, media ownership/replacement/removal, password/Host/CSRF controls, traversal/body-limit rejection, and revocation during an arriving request body. A measured single-client localhost run on Node 24.12 used the synthetic 12-dancer/6-formation demo, 12 sequential observations per operation: read median 0.76 ms / p95 1.77 ms; autosave 2.99 / 3.23 ms; publish 2.84 / 3.84 ms. These are development-machine observations, not concurrent-load, phone, or hosted capacity guarantees; the test reports fresh timings on each run.

Prototype limits: one local owner plus bearer reader capabilities, unverified supplied names rather than individual roster accounts, basic audio signature checks rather than trusted decoding/transcoding, client-derived waveform/duration, no production hosting or offline caching/synchronization. The shared TypeScript checker evaluates saved polylines numerically; the exact rational validator and worker architecture below remain target design. Reader media access follows the current published snapshot; publishing replacement/removal stops new fetches of the old track, while historical files remain immutable for the editor. Already downloaded copies cannot be retracted. Passwordless access is loopback-only with Host/forwarding checks; external binding requires `OWNER_PASSWORD` and remains a prototype configuration. The later sections describe the hosted target and its acceptance gates, not a claim those services or stronger guarantees already exist.

## 1. Product boundary and deployable shape

Build for one small school group first: Next.js React web on desktop and React Native with Expo on mobile, sharing one backend. Laptop editing exposes the stage, named cast, titled choreography sections, formation holds, transition paths, count ruler, locks, and audio. Mobile supports published playback, dancer focus, comments, revision acknowledgments, and authorized numeric waypoint/time edits through the same API; dense path editing remains a laptop workflow. A cast member is a persistent UUID with a display name, independent of an optional login account. Renaming or moving a dancer never changes identity.

Use TypeScript, Next.js web/API, managed Supabase Postgres/Auth/private object storage, and a separate long-running Node worker using the same versioned geometry package. Deploy web and worker as two Docker services on one managed container host, near the database. Postgres is the durable job queue; Redis, a vector database, a separate Python service, and realtime coediting are unnecessary for this pilot. Pin supported runtime and database versions at implementation time. Next.js supports container deployment; Supabase storage supports access policies through Postgres RLS. [Next.js deployment](https://nextjs.org/docs/app/getting-started/deploying), [Supabase storage access](https://supabase.com/docs/guides/storage/security/access-control).

Use a workspace monorepo with `apps/web`, `apps/mobile`, `apps/worker` and pure TypeScript packages for document schemas/model, musical time, saved-path evaluation, and the API client. Keep native/browser rendering and audio-clock adapters separate; the server remains authoritative. Expo supports workspace monorepos. Mobile navigation is portrait; editor and viewer routes request landscape using native per-screen options. If the actual viewport remains portrait, show an accessible rotate prompt/gate rather than a compressed editor/viewer. Orientation requests can be refused, particularly in resizable windows; observe viewport dimensions, respect safe areas/tablets, preserve current seek/selection/unsaved draft across rotation, and restore portrait navigation on exit. [Expo monorepos](https://docs.expo.dev/guides/monorepos/), [Expo screen orientation](https://docs.expo.dev/versions/latest/sdk/screen-orientation/).

The web service owns authentication, authorization, draft transactions, publication, and media URL issuance. The worker owns bounded solving, continuous geometry validation, and optional audio metadata processing. Neither browser nor worker decides which draft becomes published. External auth/storage are pragmatic managed dependencies; retaining SQL migrations, portable containers, and object keys avoids making the solver depend on a particular host.

Initial supported envelope: 4–24 dancers, rectangular stage up to 30 × 30 m, up to 80 formations and 10 minutes of audio, one constant tempo, and straight or piecewise-linear routes. A group may contain several routines, but only one solve per routine runs at a time. These are proposed product caps, not measured capacity. Scope excludes biomechanical safety guarantees, automatic choreography, variable-tempo detection, video pose analysis, and a claim of “AI.”

## 2. Source of truth and storage

Postgres stores authoritative choreography and permissions. Client state is a working copy. Published revisions and solver outputs are immutable; playback consumes stored routes and never recomputes them. Coordinates are integer millimetres in a documented stage coordinate system; time is integer ticks at 480 ticks per quarter-note beat. JSON snapshots have an explicit schema version and canonical serialization for hashing. Database timestamps serve auditing, never musical timing.

| Entity                              | Essential fields / invariants                                                                                                                                                                                                                                                                      |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `groups`, `memberships`             | UUIDs; unique group/user; owner, editor, dancer roles; membership status. Last owner cannot be removed.                                                                                                                                                                                            |
| `routines`                          | group, name, `draft_version`, `draft_document`, `published_revision_id`; one mutable draft row, optimistic concurrency.                                                                                                                                                                            |
| `cast_members`                      | routine, immutable UUID, display name, optional user ID, archived flag. Referenced members are archived, not removed from history.                                                                                                                                                                 |
| Draft document                      | stage dimensions; static exclusion polygons; cast attributes/radii; music asset reference; tempo and offset; first-class `sections: {id,title,startTick,endTick}[]`; ordered hold/transition intervals; formation positions; constraints and locks. Server validates every reference and interval. |
| `solve_jobs`                        | routine, immutable input snapshot/hash, base draft version, solver/validator versions, seed/config, status, lease token/expiry, attempts, result reference, diagnostic code.                                                                                                                       |
| `path_sets`                         | immutable input hash, per-dancer timed vertices, validity report, minimum clearances, solver version, output hash. Validated output is distinct from candidate output.                                                                                                                             |
| `revisions`                         | routine, monotonically increasing revision number, full document and cast snapshot, evaluated path set, validation/review status, immutable audio asset/version/hash, author, publication time, schema version. Unique routine/revision.                                                           |
| `comments`                          | routine, revision ID, optional cast UUID/section ID, absolute tick or tick interval, text, author, resolved state, timestamps. A section reference supplements the absolute anchor. Anchors remain on their original revision; later revisions show them only with explicit context.               |
| `revision_acknowledgments`          | unique revision/user, explicit acknowledgment timestamp; user may acknowledge only for themself. Viewing a page is not acknowledgment. Editors can read the routine's acknowledgment roster.                                                                                                       |
| `conflict_reviews`                  | motion-input/path/report hashes, conflict ID and tick/cast anchors, reviewer, reason, timestamp. Immutable decisions cover only specified model-clearance/speed conflicts in that exact evaluated motion snapshot.                                                                                 |
| `media_assets`                      | group/routine, opaque object key, content hash, size/type/duration, processing state, creator, immutable version.                                                                                                                                                                                  |
| `invites`, `read_links`             | hashed random token, scope, expiry/revocation, allowed role, bounded redemption count; invitations optionally bound to recipient email.                                                                                                                                                            |
| `mutation_receipts`, `audit_events` | unique routine/client-operation ID and returned version for retry deduplication; security/publication events without tokens or audio contents.                                                                                                                                                     |

Keeping the draft as one validated document makes atomic timeline edits and snapshots simple within this envelope. Relational rows hold identities, permissions, jobs, comments, and publication pointers. Avoid two competing editable representations of the timeline. Mutation handlers validate the document schema and semantic invariants, including active cast membership, complete routes, nonoverlapping timeline intervals, and stage bounds.

Sections such as Intro, Verse 1, and Chorus span all tracks and contain multiple formations/transitions. Store stable section UUIDs, nonempty titles, and integer half-open ranges with `0 ≤ startTick < endTick ≤ routineEndTick`; ranges cannot overlap. Default sections contiguously cover the routine. All sections use one routine-global clock: counts, paths, audio, and note anchors never reset at a section boundary. Render each title at the region's top-left with subtle full-height boundaries. An ordinary boundary edit changes grouping/labels only, atomically adjusting adjacent sections to retain coverage; it never moves/warps paths or audio. An explicit retime is a separate explicit mutation that changes motion inputs and requires reevaluation. Section focus/loop playback uses the absolute range in MVP; reordering and ripple edits are later scope. Title/grouping changes update the draft version and publication snapshot but do not change the motion-input hash or force a new solve.

## 3. API, autosave, and publication

All application writes go through authenticated server endpoints and transactional operations. The server verifies the auth token, loads current membership, and checks scope on every request. Read links use a separate narrow reader path. Suggested operations:

| Operation                                     | Contract                                                                                                                                                                         |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /routines/:id/draft`                     | Document, version, capabilities; editors only. Dancers read published content.                                                                                                   |
| `PATCH /routines/:id/draft`                   | Typed command batch, expected version / `If-Match`, client operation ID. Atomically validate, compare-and-swap, increment version, and invalidate incompatible solve attachment. |
| `POST /routines/:id/solves`                   | Expected version and idempotency key; persist immutable input and queue job in one transaction; return job ID.                                                                   |
| `GET /solves/:id`                             | Authorized status, bounded diagnostics, stored candidate or validated result. Poll with backoff; realtime status is optional later.                                              |
| `POST /routines/:id/apply-solve`              | Expected draft version plus matching job/input hash; explicitly attach validated paths. A stale result remains inspectable but cannot silently replace newer edits.              |
| `POST /routines/:id/publish`                  | Expected version; owner/editor permission; validate snapshot, paths, and ready audio; create immutable revision and update publication pointer atomically.                       |
| `GET /routines/:id/published`                 | Latest revision metadata, ETag, capabilities; immutable revision endpoint returns the exact content.                                                                             |
| `POST /revisions/:id/comments`                | Authenticated permitted member; validated tick/cast anchor. Read links cannot comment.                                                                                           |
| `PUT /revisions/:id/acknowledgment`           | Idempotent explicit action by the authenticated member; never triggered on open/playback. Each revision needs its own acknowledgment. Read links cannot acknowledge.             |
| `POST /routines/:id/conflict-reviews`         | Owner/editor, expected draft version and exact evaluated hashes; explicit anchored reason for each reviewable conflict. No bulk implicit approval.                               |
| `POST /media/uploads` / `complete`            | Scoped upload ticket; finalize only after server verifies object metadata and decoding.                                                                                          |
| Invite/redeem/revoke; read-link create/revoke | Owner-managed access, with transactional redemption limits and audit trail.                                                                                                      |

Debounced autosave submits small command batches. A version mismatch returns `409` with the current version; the client retains unsent commands and lets the editor compare/reapply against fresh state. No last-write-wins overwrites, and no automatic merge of overlapping stage/timeline edits. Revoked permissions return `403`; retain a private local recovery copy without retrying privileged writes. HTTP retries with the same operation ID return the original result. Presence may warn about another editor, but version checks enforce correctness. Local undo produces new commands; it cannot rewrite revision history.

Publishing freezes names, counts, music, constraints, and routes together. Dancers open a stable “latest published” link, see revision number/time, and check for updates on open, focus, reconnect, and periodically while online. During playback an available update prompts a deliberate reload so a routine does not change mid-run. Pinned revision links always show their revision and query the latest pointer when connected. Draft edits cannot leak to dancers.

Publication requires a continuous evaluation matching current motion inputs. A model-valid revision has no constraint conflicts. An owner/editor may instead publish deliberate close interaction or model-speed exceptions only after explicitly reviewing every clearance/speed conflict with its dancer/tick anchor and reason. Label the revision “published with reviewed model conflicts,” preserve prominent warnings and review details in mobile playback, and never mark its paths model-valid or safe. Schema errors, missing/discontinuous routes, invalid timing, stage/exclusion-boundary violations, unmet explicit locks/corridors, and absent required media remain publication blockers; changing those constraints requires an explicit draft edit and new evaluation. Motion/path/report hash changes invalidate prior review decisions, and publishing rechecks permissions/version and reviews atomically. This separates artistic decisions from the planner's model without hiding unresolved conflicts.

## 4. Counts, audio, and deterministic paths

Use zero-based musical tick internally. Display eight-count labels independently: tick `0` is `1:1`, tick `8×480` is `2:1`. MVP tempo is an explicit integer microseconds-per-beat value; preserve this value when displaying rounded BPM. If audio offset `a` is the audio timestamp of beat zero, then `audio_us(t) = a + t × us_per_beat / 480`. Negative offset/count-in is allowed and produces silent preroll before audio begins. Validate that the final timeline lies within available playback coverage or explicit silence. Count labels never imply a time signature; document the quarter-note unit in the UI. Tempo maps can later use piecewise integration without changing stored ticks.

Use the audio clock as playback reference when audio is active; seeking uses the same formula. Without audio, during silent preroll, or when autoplay is blocked, offer an explicit keyboard/screen-reader-accessible silent Play control using a monotonic elapsed-time clock; label silent playback and do not advance unexpectedly. Pause/seek/resume or clock switching preserves the current tick and reanchors elapsed time. At rehearsal playback rate `s`, ticks advance at `480 × s / us_per_beat` per wall-clock microsecond; model speed remains `distance_mm / (delta_ticks × us_per_beat / 480) × 1000` metres/second at rate 1, and scales by `s` for rehearsal preview. Audio and visuals share the selected rate. There is no cross-device synchronized rehearsal clock. Changing tempo, stage, cast radius, positions, constraints, transition duration, or any manual waypoint coordinate/tick invalidates attached evaluation and affected timing/conflict reviews until reevaluated. Audio replacement/offset changes also invalidate combined playback readiness.

Each formation has an explicit hold `[start,end)` and a transition to the next hold. Holds fix all dancer positions; transitions contain timed piecewise-linear paths, including deliberate waits. Constraints include exact start/end, stage bounds, static obstacles, minimum pair clearance, maximum modelled speed, locked dancer waypoints/routes, and optional corridor constraints. Distinguish hard constraints from soft objectives such as route length and waiting. An impossible lock is reported; the solver never removes it. No unlock, reassignment of named dancers, or timing extension happens implicitly.

Phase 1 uses deterministic bounded waypoint/time-grid search with fixed dancer ordering, fixed tie breaks, integer costs, versioned search limits, and a seeded, bounded repair pass. It may miss feasible solutions; statuses must distinguish `validated`, `no_solution_found_within_budget`, `invalid_input`, `timeout`, and `failed`. Never label a timeout “physically impossible.” Start/end conflicts are rejected before searching. Manually edited paths use the same validator. Preview candidates remain visibly unvalidated until acceptance.

Curved-looking drawing tools deterministically tessellate their curves to saved, timed, quantized polylines before evaluation. The saved polyline is the playback trajectory on every device. Do not apply CSS/SVG smoothing that changes it; a visually smoother trajectory needs its own stored vertices and fresh evaluation. A solver failure can lead to a manually authored, fully evaluated route and explicit conflict review; failure alone never supplies publishable paths.

Persist the complete canonical input: geometry, ordered cast IDs/radii, timing/tempo, constraints/locks, search grid/config, solver version/build, validator version, and seed. Exclude timestamps/job IDs from the content hash. Each output stores every timed vertex plus diagnostics. Duplicate content may reuse a validated result only when all version/config hashes match. Golden fixtures must reproduce the same output hash across supported deployments.

Continuous evaluation is a publication gate, not a few animation samples. Model each dancer as a horizontal disc with configurable radius plus an explicit clearance margin. For every dancer pair, split time at the union of their path vertices. On each interval relative position is linear, `r(u)=r0+u·v`; evaluate squared distance at both ends and at `u=clamp(-r0·v/(v·v),0,1)` when `v≠0`. Compare against squared required separation. Integer coordinates/ticks permit exact rational comparisons using BigInt, including tangencies and zero-duration rejection. Check every segment against the stage inset and inflated static obstacles, including stationary holds, plus speed limits using tempo. Evaluate the final saved, quantized output, not pre-rounding candidates. Independent validator code must reject malformed/missing paths and nonfinite data; review decisions never alter its measured report.

Only a conflict-free report certifies continuous clearance for the specified disc/linear-motion model; reviewed exceptions do not. Neither status certifies human safety, body articulation, floor conditions, acceleration, or adherence during rehearsal. Piecewise-linear corners can imply instantaneous direction changes; pilot UI must show route timing and allow slower transitions, and real movement review remains a release requirement. Higher-order motion requires a corresponding continuous validator before being offered.

## 5. Jobs, access, offline, and operations

Workers claim jobs with `FOR UPDATE SKIP LOCKED`, set a lease/fencing token, commit, and solve outside the transaction. A heartbeat extends the lease; expired jobs retry at most twice. Only the current token may commit an immutable result; cancellation and stale attempts cannot attach output. Queue fairness limits concurrent jobs per group; new requests may cancel superseded queued work. Start with one worker/concurrent solve, a 10-second soft search budget and 30-second wall timeout per transition, bounded nodes/memory, and a 120-second routine cap. Instrument rather than promise those targets. PostgreSQL locking supports this queue pattern; transactional locks should remain short. [PostgreSQL explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html).

Owner manages membership, links, routine deletion, and ownership transfer; editor edits/publishes/invites nobody; dancer reads published plans and comments. Optional cast-to-account assignment enables “my path,” without exposing emails. Invitations grant only dancer/editor access, expire, and require login plus email match when bound. Read links are high-entropy bearer capabilities scoped to one routine’s published content, optionally one fixed revision, with expiry/revocation; no drafts, member directory, comments, or mutation. Use link token exchange into a scoped HttpOnly session and remove the token from the address bar; set no-referrer and exclude third-party analytics on exchange pages.

Enable RLS on all exposed tables and private storage; no direct client database writes. The web database role has no RLS bypass and sets the server-verified user identity transaction-locally; policies check current group membership. Client credentials cannot obtain this DB connection. Read-link retrieval uses a narrowly scoped server function; the worker role can claim jobs/read job snapshots/write results, but cannot publish or manage membership. Keep privileged provider keys server-only; scope security-definer functions, fixed search paths, and grants explicitly. Test both API authorization and underlying policy denial. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Store audio in private object storage under immutable opaque keys; serve short-lived signed URLs only after permission checks, including range playback. Upload cap: 30 MB and 10 minutes, accepted MP3/M4A/WAV signatures plus actual decoder verification; reject failed decodes and bound processing resources. Keep original and playback rendition hashes distinct. Publication requires a ready browser-playable rendition and measured duration when music is attached; explicitly silent routines may omit audio. Never overwrite an object used by a revision. Garbage collection deletes abandoned uploads after a grace period and referenced media only after retention rules permit. Audio caching is explicit because it consumes device space and may have rights restrictions; no downloaded third-party dataset is required.

Offline support is a read-only cached published revision and optional downloaded audio, with revision number, last-check time, and a persistent “offline; updates not checked” indicator. No offline edits, comment queue, merge protocol, or implied latest-plan guarantee. Purge caches on sign-out where possible. Revocation prevents new fetches but cannot retract an already downloaded copy; links and onboarding must make this property clear.

## 6. Hosted release gates

Use versioned SQL migrations with constraints and RLS tests; apply to staging first. Document/snapshot schema migrations must retain the original published payload and offer versioned readers, never silently rewrite old choreography. Deploy backward-compatible expand/contract migrations before code that needs them. Pin build artifacts, separate staging/production credentials, and record solver versions. Back up Postgres and media, then verify a restore that preserves revision/media references. Log request/job IDs, timings, retries, failures, and publication versions without names, tokens, or audio payloads.

The only initial benchmark corpus is explicitly synthetic, seeded and checked into the repository: crossing pairs, symmetric swaps, bottlenecks, waits, locked routes, stationary holds, impossible overlap, near tangency, stage boundaries, duplicate retries, and stale jobs. No real data has been downloaded or used for training. Later consented rehearsal measurements may calibrate speeds/radii and evaluate usability; they do not retroactively establish a physical safety guarantee or constitute a trained model by default.

Release requires: property/golden tests for geometry and time conversions; independent continuous validation against adversarial mid-segment collisions; deterministic output checks; edit-vs-publish/job race tests; tenant/role/link/media denial tests; expired invite/session tests; web/native audio/silent-clock seek/resume checks on target phones; orientation refusal, safe-area, and state-retention checks; section range/global-clock/loop and non-retiming boundary tests; two-editor conflict recovery without lost work; review invalidation and warning retention; explicit per-revision acknowledgment tests; offline revision labeling; restore/migration rehearsal; synthetic 24-dancer workload profiling and graceful budget failures; and an end-to-end school pilot from invite through publish, dancer playback, acknowledgment/comment, corrected revision, and update notice. Set measured latency/memory budgets from that run before lifting caps. Local tests above cover a subset; the complete hosted release gates have not been demonstrated end to end.
